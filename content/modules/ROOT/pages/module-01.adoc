= Two Containers, One Application

Your web service is two pieces. There is a web frontend that serves pages, and a data store that holds its state. For lifecycle management the pieces run as two containers: they are built, updated, and fail together — and to work at all, they need to communicate.

In this module you will run the two containers the usual way, and find out that two containers on one machine still cannot talk to each other.

The images this lab uses are minimal: no shell, no package manager, running as non-root users on unprivileged ports. You configure them with environment variables, and you work with them from the outside — there is no logging into these containers.

== Verify the Podman Installation

Confirm the version of Podman on this system.

[source,bash,role=execute]
----
podman --version
----

[source,text]
----
podman version 5.x.x
----

Podman 5 is the current major version on RHEL 10.

== Run the Pieces

Run the web frontend and the data store in the usual fashion — as two independent containers. The `--rm` flag removes a container automatically when it stops, so these throwaway containers never need to be cleaned up by hand.

[source,bash,role=execute]
----
podman run -d --rm --name web -p 8000:8000 webcounter-app:latest
----

[source,bash,role=execute]
----
podman run -d --rm --name store registry.access.redhat.com/hi/valkey:latest
----

Check what is running:

[source,bash,role=execute]
----
podman ps
----

[source,text]
----
CONTAINER ID  IMAGE                                   COMMAND          CREATED         STATUS         PORTS                     NAMES
b1e2f3a4c5d6  webcounter-app                          gunicorn app.a   5 seconds ago   Up 5 seconds   0.0.0.0:8000->8000/tcp    web
9a8b7c6d5e4f  registry.access.redhat.com/hi/valkey    valkey-server    3 seconds ago   Up 3 seconds   6379/tcp                  store
----

Two containers, both healthy, both running on this one machine.

== The Pieces Cannot Talk

From the host, load the page:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: —</p>
<p>The web frontend cannot reach its data store at localhost:6379.</p>
</body>
</html>
----

The page is served — the frontend is up — but it cannot reach its own data store. Both containers are running on the same machine, yet the frontend's `localhost` is its own container, and the store is not there.

The frontend's own logs say the same:

[source,bash,role=execute]
----
podman logs web
----

[source,text]
----
[store unreachable] dial tcp 127.0.0.1:6379: connect: connection refused
----

There is no shell to enter in these images — what the application writes to its logs is the debugging surface. The logs confirm what the page showed: in the usual fashion, every container is its own localhost.

The pieces need to communicate. How two containers on one machine find each other is the next module.
