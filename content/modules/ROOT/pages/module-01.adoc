= Two Containers, One Application

Your web service is two pieces. There is a web frontend that serves pages, and a data store that holds its state. For lifecycle management the pieces run as two containers: they are built, updated, and fail together — and to work at all, they need to communicate.

In this module you will connect the pieces: a Podman network gives them somewhere to find each other, and their container names give them a way.

The images this lab uses are minimal: no shell, no package manager, running as non-root users on unprivileged ports. You configure them with environment variables, and you work with them from the outside — there is no logging into these containers.

== Verify the Podman Installation

Confirm the version of Podman on this system.

[source,bash,role=execute]
----
podman --version
----

[source,text]
----
podman version 5.x.x
----

Podman 5 is the current major version on RHEL 10.

== Create a Network

The frontend needs to talk to the store: it reads its state from the store on every page load. The store's location is the `STORE_HOST` environment variable — and when `STORE_HOST` is not defined, it is `localhost`, the frontend's own container. What it has, so far, is Podman's default network:

----
+------------------------------------------------------------------+
|                              host                                |
|                                                                  |
|   +-------------------------------+  +---------------------+     |
|   |  web                          |  |  store              |     |
|   |  gunicorn :8000               |  |  valkey :6379       |     |
|   |                               |  |                     |     |
|   |  reads its state from the     |  |  listening on       |     |
|   |  store at STORE_HOST:6379     |  |  its own localhost  |     |
|   |                               |  |                     |     |
|   |  STORE_HOST defaults to       |  |                     |     |
|   |  localhost:6379               |  |                     |     |
|   +-------------------------------+  +---------------------+     |
+------------------------------------------------------------------+
----

So the frontend's default target — its own localhost:6379 — is where no store is: from inside the web container, `localhost` is the web, not the store. And the store's assigned address changes every time its container is recreated. What the frontend needs is a name for the store, on a network both containers join. The simplest way is a Podman network:

[source,bash,role=execute]
----
podman network create app-net
----

A user-defined network is different: containers join it by choice, and Podman runs DNS on it so container names resolve.

== Run the Frontend

Run the frontend on the new network. The `--rm` flag removes a container automatically when it stops, so these containers never need to be cleaned up by hand. The store location is an environment variable, read when the container starts:

[source,bash,role=execute]
----
podman run -d --rm --name web -p 8000:8000 --network app-net -e STORE_HOST=store webcounter-app:latest
----

One piece of configuration: `STORE_HOST=store` — the store's container name. The frontend is now set to find its store by name on this network, and no container by that name is on it yet.

== Check the Log

There is no shell to enter in these images — what the application writes to its logs is the debugging surface. Check it:

[source,bash,role=execute]
----
podman logs web
----

[source,text]
----
[2026-10-20 13:29:02 +0000] [1] [INFO] Starting gunicorn 23.0.0
[2026-10-20 13:29:02 +0000] [1] [INFO] Listening at: http://0.0.0.0:8000 (1)
[2026-10-20 13:29:02 +0000] [1] [INFO] Using worker: sync
[2026-10-20 13:29:02 +0000] [2] [INFO] Booting worker with pid: 2
[2026-10-20 13:29:02 +0000] [3] [INFO] Booting worker with pid: 3
[store unreachable] Error -2 connecting to store:6379. Name or service not known.
[store unreachable] Error -2 connecting to store:6379. Name or service not known.
----

The name `store` does not resolve. The frontend is on the network, but nothing by that name is — DNS on a user-defined network resolves container names, and only for containers on that network.

== Start the Store

Run the store the usual way — the default network, joined automatically. One flag: valkey's protected mode only accepts connections from its own loopback, and the frontend connects over the network:

[source,bash,role=execute]
----
podman run -d --rm --name store registry.access.redhat.com/hi/valkey:latest --protected-mode no
----

The store is running, but on the default network, so the name `store` still does not resolve on `app-net`. Join the running container to the new network — the other way a container joins: at start the frontend took `--network`; a running container takes `podman network connect`, no recreation:

[source,bash,role=execute]
----
podman network connect app-net store
----

== Networking Works

From the host, the page:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: 1, served from store at store:6379</p>
</body>
</html>
----

Load it again:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: 2, served from store at store:6379</p>
</body>
</html>
----

The moment the store joined the network, the name resolved and the page worked — the startup log's unresolvable name now answers on every page load. The frontend reaches the store at `store:6379`, the container's name resolved through the network's DNS: two containers on a shared network, finding each other by name, talking on every page load.

== Two Containers Are Still Two Containers

Networking solved communication. Look at what you are managing, though: two separate start commands, two lifecycles to stop and start, a store name wired into an environment variable, the frontend's port published container by container. As an application, the pieces are not coordinated — they are two containers that happen to be on the same network.

An application is one thing: one lifecycle, one network view, hostnames the pieces agree on. That is what the next module adds.
