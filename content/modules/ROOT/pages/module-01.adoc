= Two Containers, One Application

Real world services are usually made up of more than one component.
There is a web frontend that serves pages, and a data store that holds its state. 
Typically each of these would be packaged as a separate container, so how do we treat them as a single application instead?

In this lab, you'll look at how to connect the pieces into a single unit that can communicate the same way they would if on a single host.

The images this lab uses are minimal: no shell, no package manager, running as non-root users on unprivileged ports. 
The application is a simple gunicorn frontend that reads and stores data in a valkey database.
There are simple configuration options available via environment variables.

== The configuration we need

The gunicorn `web` container gets the address of the valkey `store` container in two ways.
Either the store's location is in the `STORE_HOST` environment variable or when that's not defined, it is `localhost`.
The valkey server is configured to only listen on `localhost`.
Since this is container networking, that refers to `localhost` inside of the container, not from the host view.

----
+------------------------------------------------------------------+
|                              host                                |
|                                                                  |
|   +-------------------------------+  +---------------------+     |
|   |           web                 |  |       store         |     |
|   |  gunicorn :8000               |  |  valkey :6379       |     |
|   |                               |  |                     |     |
|   |  store at STORE_HOST:6379     |  |  listens on         |     |
|   |                               |  |  localhost          |     |
|   +-------------------------------+  +---------------------+     |
+------------------------------------------------------------------+
----

Not only will these containers have isolated networks by default, they'll also get different IPs every time they're restarted.
We want to be able to refer to them by "hostnames", or rather the assigned container name.

== Create a new network

One important way that user-defined networks differ from the `default` network is `podman` will provide DNS resolution for container names. 

We can create a new network with `podman` that these two containers will be able to join.
[source,bash,role=execute]
----
podman network create app-net
----


== Run the Frontend

Launching this container is just like any other, we provide some options to provide the name, publish a port, and to join a specific network.

[source,bash,role=execute]
----
podman run -d --rm \
  --name web -p 8000:8000 \
  -e STORE_HOST=store \
  --network app-net \
  ghcr.io/rhel-labs/webcounter-app:latest
----
.The flags
* -d        run in the background
* --rm      remove on exit
* --name    assign the resolvable name
* -p        publish ports, format `host port:container port`
* -e        set the environment variable
* --network join the named network instead of `default`

Since we passed the environment variable, the application will now be looking for a host named `store` instead of `localhost`. 
We've published the port the application listens on so we will be able to connect to it from the outside world.

== Start the Store

The `store` container will learn about its network the same way as the web frontend, the `--network` flag.
Otherwise, there's no other options for `podman` to add.
By design in this image, valkey's protected mode only accepts connections from its loopback.
We can pass arguments to `valkey` after the name of the image, this will disable protected mode.
Many other images and applications can take arguments to their `CMD`, but refer to the documentation for each one.
The important takeaway is that everything up to the image name is an option for `podman` and everything after it gets passed to the image at startup.

[source,bash,role=execute]
----
podman run -d --rm \
  --name store \
  --network app-net \
  registry.access.redhat.com/hi/valkey:latest --protected-mode no
----

== Two Containers Are Still Two Containers

Networking solved communication between our two components. 
As an application, the pieces are not coordinated, they are two containers that happen to be on the same network.
We needed two separate commands to start them, environment variables to configure, and a network to manually manage.


An application is one thing: one lifecycle, one network view, hostnames the pieces agree on. 
Let's explore an approach in the next exercise that makes these two components into a more cohesive thing, a `pod`.
