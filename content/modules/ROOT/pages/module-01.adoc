= Grouping Containers into Pods

Your web service is two pieces. There is a web frontend that serves pages, and a data store that holds its state. They are one application: they are deployed together, they fail together, and they talk to each other constantly.

This is a two-container application, and running the two containers in the usual fashion does not let them talk to each other. Each container gets its own network view: its own localhost, its own address — an address that changes every time the container is recreated. In this module you will deploy both pieces the usual way, see why they cannot talk, and group them into a pod.

The images this lab uses are minimal: no shell, no package manager, running as non-root users on unprivileged ports. You configure them with environment variables, and you work with them from the outside — there is no logging into these containers.

== Verify the Podman Installation

Confirm the version of Podman on this system.

[source,bash,role=execute]
----
podman --version
----

[source,text]
----
podman version 5.x.x
----

Podman 5 is the current major version on RHEL 10.

== Run the Pieces in the Usual Fashion

First, run the web frontend and the data store in the usual fashion — as two independent containers. The `--rm` flag removes a container automatically when it stops, so these throwaway containers never need to be cleaned up by hand.

[source,bash,role=execute]
----
podman run -d --rm --name web -p 8000:8000 webcounter-app:latest
----

[source,bash,role=execute]
----
podman run -d --rm --name store registry.access.redhat.com/hi/valkey:latest
----

Check what is running:

[source,bash,role=execute]
----
podman ps
----

[source,text]
----
CONTAINER ID  IMAGE                                   COMMAND          CREATED         STATUS         PORTS                     NAMES
b1e2f3a4c5d6  webcounter-app                          gunicorn app.a   5 seconds ago   Up 5 seconds   0.0.0.0:8000->8000/tcp    web
9a8b7c6d5e4f  registry.access.redhat.com/hi/valkey    valkey-server    3 seconds ago   Up 3 seconds   6379/tcp                  store
----

Two containers, both healthy, both running on this one machine.

== The Pieces Cannot Talk

From the host, load the page:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: —</p>
<p>The web frontend cannot reach its data store at localhost:6379.</p>
</body>
</html>
----

The page is served — the frontend is up — but it cannot reach its own data store. Both containers are running on the same machine, yet the frontend's `localhost` is its own container, and the store is not there. Running the two containers in the usual fashion gives you two healthy containers that cannot talk to each other.

The frontend's own logs say the same:

[source,bash,role=execute]
----
podman logs web
----

[source,text]
----
[store unreachable] dial tcp 127.0.0.1:6379: connect: connection refused
----

There is no shell to enter in these images — what the application writes to its logs is the debugging surface. The logs confirm what the page showed: the store is not at the frontend's `localhost`, because in the usual fashion, every container is its own localhost.

== Create a Pod

A pod is a group of containers that share a single network namespace — one IP address, one localhost, one lifecycle.

[source,bash,role=execute]
----
podman pod create --name webapp
----

You now have an empty pod:

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED         INFRA ID      # OF CONTAINERS
7f6e5d4c3b2a  webapp      Created     3 seconds ago   c1d2e3f4a5b6  1
----

Notice the `# OF CONTAINERS` column: the pod already contains one container that you did not start.

== Run the Pieces Inside the Pod

The standalone containers are no longer needed — because they were started with `--rm`, stopping them removes them:

[source,bash,role=execute]
----
podman stop web store
----

Now run both pieces inside the pod. Adding a container to a pod takes a single flag:

[source,bash,role=execute]
----
podman run --pod webapp -d --rm --name web webcounter-app:latest
----

[source,bash,role=execute]
----
podman run --pod webapp -d --rm --name store registry.access.redhat.com/hi/valkey:latest
----

[source,bash,role=execute]
----
podman ps
----

[source,text]
----
CONTAINER ID  IMAGE                                   COMMAND          CREATED         STATUS         PORTS       NAMES
e4f5a6b7c8d9  webcounter-app                          gunicorn app.a   8 seconds ago   Up 8 seconds               web
2c3d4e5f6a7b  registry.access.redhat.com/hi/valkey    valkey-server    6 seconds ago   Up 6 seconds   6379/tcp    store
c1d2e3f4a5b6  localhost/podman-pause                  ...              2 minutes ago   Up 2 minutes               7f6e5d4c3b2a-infra
----

== The Infra Container

There is a third container: `7f6e5d4c3b2a-infra`, running an image called `podman-pause`.

That is the infra container, and it *is* the pod. It runs a tiny process whose only job is to hold open the namespaces the pod's containers share — the network namespace in particular. Because `web` and `store` join the infra container's namespaces instead of creating their own, they share one IP address and one localhost.

The infra container is why pods work: it exists for as long as the pod does, and every container in the pod comes and goes inside the boundaries it holds. When the pod stops, the infra container stops, and the shared network view disappears with it.

== Inspect the Pod

`podman pod ps` gives the summary view:

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED         INFRA ID      # OF CONTAINERS
7f6e5d4c3b2a  webapp      Running     3 minutes ago   c1d2e3f4a5b6  3
----

Inspect the pod, filtered to the state of the application:

[source,bash,role=execute]
----
podman pod inspect webapp --format '{{.State}} {{.NumContainers}}'
----

[source,text]
----
Running 3
----

Running, with three containers: the two pieces and the infra container. One line — the state of the whole application.

== The Pieces Talk

Inside a pod, all containers share one localhost — and the store listens on 6379. The frontend's startup log shows it found the store:

[source,bash,role=execute]
----
podman pod logs webapp
----

[source,text]
----
---2c3d4e5f6a7b---
1:M 19 Oct 2026 * Ready to accept connections tcp
---e4f5a6b7c8d9---
store reached at localhost:6379
----

One command returned the logs of every container in the pod — the store's startup line and the frontend's. `store reached at localhost:6379`: no addresses, no published ports, just the shared localhost the infra container provides. The pod is what let the pieces talk.

But logs are the only window into this pod. From the host, the page is still unreachable — the pod has published nothing, and nothing gets in unless you open it. That is the next module.
