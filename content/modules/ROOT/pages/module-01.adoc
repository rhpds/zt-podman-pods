= Two Containers, One Application

Your web service is two pieces. There is a web frontend that serves pages, and a data store that holds its state. For lifecycle management the pieces run as two containers: they are built, updated, and fail together — and to work at all, they need to communicate.

In this module you will run the two containers the usual way, find out that two containers on one machine still cannot talk to each other, and explore container networking until they can.

The images this lab uses are minimal: no shell, no package manager, running as non-root users on unprivileged ports. You configure them with environment variables, and you work with them from the outside — there is no logging into these containers.

== Verify the Podman Installation

Confirm the version of Podman on this system.

[source,bash,role=execute]
----
podman --version
----

[source,text]
----
podman version 5.x.x
----

Podman 5 is the current major version on RHEL 10.

== Run the Pieces

Run the web frontend and the data store in the usual fashion — as two independent containers. The `--rm` flag removes a container automatically when it stops, so these throwaway containers never need to be cleaned up by hand.

[source,bash,role=execute]
----
podman run -d --rm --name web -p 8000:8000 webcounter-app:latest
----

[source,bash,role=execute]
----
podman run -d --rm --name store registry.access.redhat.com/hi/valkey:latest
----

Check what is running:

[source,bash,role=execute]
----
podman ps
----

[source,text]
----
CONTAINER ID  IMAGE                                   COMMAND          CREATED         STATUS         PORTS                     NAMES
b1e2f3a4c5d6  webcounter-app                          gunicorn app.a   5 seconds ago   Up 5 seconds   0.0.0.0:8000->8000/tcp    web
9a8b7c6d5e4f  registry.access.redhat.com/hi/valkey    valkey-server    3 seconds ago   Up 3 seconds   6379/tcp                  store
----

Two containers, both healthy, both running on this one machine.

== The Pieces Cannot Talk

From the host, load the page:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: —</p>
<p>The web frontend cannot reach its data store at localhost:6379.</p>
</body>
</html>
----

The page is served — the frontend is up — but it cannot reach its own data store. Both containers are running on the same machine, yet the frontend's `localhost` is its own container, and the store is not there.

The frontend's own logs say the same:

[source,bash,role=execute]
----
podman logs web
----

[source,text]
----
[store unreachable] dial tcp 127.0.0.1:6379: connect: connection refused
----

There is no shell to enter in these images — what the application writes to its logs is the debugging surface. The logs confirm what the page showed: in the usual fashion, every container is its own localhost.

== Explore Networking

The frontend needs the store's location. The store has an address, but that address is assigned by Podman's network and changes every time the container is recreated — wiring a changing address into a static configuration is not coordination. What the frontend needs is a name that resolves, on a network both containers join.

[source,bash,role=execute]
----
podman network create app-net
----

So far every container has used Podman's default network, joined automatically. A user-defined network is different: containers join it by choice, and Podman runs DNS on it so container names resolve.

The frontend's store address is an environment variable, read when the container starts — so the frontend is the one piece that needs recreating. Stopping it removes it, because it was started with `--rm`:

[source,bash,role=execute]
----
podman stop web
----

[source,bash,role=execute]
----
podman run -d --rm --name web -p 8000:8000 --network app-net -e STORE_HOST=store webcounter-app:latest
----

One new piece of configuration: `STORE_HOST=store` — the store's container name, instead of the frontend's own localhost. The store keeps running, on the default network; it has not joined the new one yet.

Check the frontend's logs:

[source,bash,role=execute]
----
podman logs web
----

[source,text]
----
[store unreachable] Error -2 connecting to store:6379. Name or service not known.
----

The name `store` does not resolve. The frontend is on the new network, but the store is not on it — DNS on a user-defined network resolves container names, and only for containers on that network.

Move the running store onto it. No recreation: the store joins the network as it is:

[source,bash,role=execute]
----
podman network connect app-net store
----

== Networking Works

From the host, the page:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: 1, served from store at store:6379</p>
</body>
</html>
----

Load it again:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: 2, served from store at store:6379</p>
</body>
</html>
----

The moment the store joined the network, the name resolved and the page worked — same command as the failed startup ping, different result now. The frontend reaches the store at `store:6379`, the container's name resolved through the network's DNS: two containers on a shared network, finding each other by name, talking on every page load.

== Two Containers Are Still Two Containers

Networking solved communication. Look at what you are managing, though: two separate start commands, two lifecycles to stop and start, a store name wired into an environment variable, the frontend's port published container by container. As an application, the pieces are not coordinated — they are two containers that happen to be on the same network.

An application is one thing: one lifecycle, one network view, hostnames the pieces agree on. That is what the next module adds.
