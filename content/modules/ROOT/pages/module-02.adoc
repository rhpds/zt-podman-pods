= Exploring Container Networking

The application is two healthy containers on one machine that cannot talk: each container is its own localhost. In this module you will explore container networking until the pieces can find each other.

== The Address Is Not the Answer

The frontend needs the store's location. The store has one:

[source,bash,role=execute]
----
podman inspect store --format '{{.NetworkSettings.IPAddress}}'
----

[source,text]
----
10.88.0.4
----

That address is assigned by Podman's network — recreate the container and it will likely be different. Wiring a changing address into a static configuration is not coordination. What the frontend needs is a name that resolves, on a network both containers join.

== Create a Network

[source,bash,role=execute]
----
podman network create app-net
----

So far every container has used Podman's default network, joined automatically. A user-defined network is different: containers join it by choice, and Podman runs DNS on it so container names resolve.

== Join the Pieces by Name

Join both pieces to it — stopping them removes them, because they were started with `--rm`:

[source,bash,role=execute]
----
podman stop web store
----

[source,bash,role=execute]
----
podman run -d --rm --name store --network app-net registry.access.redhat.com/hi/valkey:latest
----

[source,bash,role=execute]
----
podman run -d --rm --name web -p 8000:8000 --network app-net -e STORE_HOST=store webcounter-app:latest
----

One new piece of configuration: `STORE_HOST=store` — the store's container name, instead of the frontend's own localhost.

== Networking Works

From the host, the page:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: 1, served from store at store:6379</p>
</body>
</html>
----

Load it again:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: 2, served from store at store:6379</p>
</body>
</html>
----

The frontend reached the store at `store:6379` — the container's name, resolved through the network's DNS. Two containers on a shared network, finding each other by name, talking on every page load.

== Two Containers Are Still Two Containers

Networking solved communication. Look at what you are managing, though: two separate start commands, two lifecycles to stop and start, a store name wired into an environment variable, the frontend's port published container by container. As an application, the pieces are not coordinated — they are two containers that happen to be on the same network.

An application is one thing: one lifecycle, one network view, hostnames the pieces agree on. That is what the next module adds.
