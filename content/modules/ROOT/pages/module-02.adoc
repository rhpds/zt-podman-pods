= Grouping Containers into Pods

The application communicates: two containers on a shared network, finding each other by name on every page load. But as an application it is not coordinated — two lifecycles, a store name wired in by environment variable, a port published per container. In this module you will group the pieces into a pod, and the pod will solve the coordination.

== Create a Pod

[source,bash,role=execute]
----
podman pod create --name webapp -p 8000:8000
----

A pod is a group of containers that share a single network namespace — one IP address, one localhost, one lifecycle. Note where the port went: on the pod, not on any container. Port publishing is a property of the pod's network namespace, held by the infra container and shared by every container in it.

You now have an empty pod:

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED         INFRA ID      # OF CONTAINERS
7f6e5d4c3b2a  webapp      Created     3 seconds ago   c1d2e3f4a5b6  1
----

Notice the `# OF CONTAINERS` column: the pod already contains one container that you did not start.

== Run the Pieces Inside the Pod

The networked containers are no longer needed — stopping them removes them, because they were started with `--rm`:

[source,bash,role=execute]
----
podman stop web store
----

Run both pieces inside the pod — and note what is missing: no `--rm` this time. In module-01 the containers were throwaway, removed the moment they stopped. These pieces are the application, and the application is something you will stop and start again — its pieces have to still be there. Adding a container to a pod takes a single flag:

[source,bash,role=execute]
----
podman run --pod webapp -d --name web ghcr.io/rhel-labs/webcounter-app:latest
----

[source,bash,role=execute]
----
podman run --pod webapp -d --name store registry.access.redhat.com/hi/valkey:latest
----

No environment variable, no network join — and no `--protected-mode no` this time. Inside the pod the pieces share one network namespace: the frontend's connection arrives on the store's own loopback, and valkey accepts loopback connections even in protected mode. The store listens on 6379, and `localhost` is the coordinated hostname — the pieces agree on it because they share the pod's network view.

== The Infra Container

There is a third container:

[source,bash,role=execute]
----
podman ps
----

[source,text]
----
CONTAINER ID  IMAGE                                   COMMAND          CREATED         STATUS         PORTS       NAMES
e4f5a6b7c8d9  webcounter-app                          gunicorn app.a   8 seconds ago   Up 8 seconds               web
2c3d4e5f6a7b  registry.access.redhat.com/hi/valkey    valkey-server    6 seconds ago   Up 6 seconds   6379/tcp    store
c1d2e3f4a5b6  localhost/podman-pause                  ...              2 minutes ago   Up 2 minutes               7f6e5d4c3b2a-infra
----

`7f6e5d4c3b2a-infra`, running an image called `podman-pause`, is the infra container — and it *is* the pod. It runs a tiny process whose only job is to hold open the namespaces the pod's containers share — the network namespace in particular. Because `web` and `store` join the infra container's namespaces instead of creating their own, they share one IP address and one localhost.

The infra container is why pods work: it exists for as long as the pod does, and every container in the pod comes and goes inside the boundaries it holds. When the pod stops, the infra container stops, and the shared network view disappears with it.

== One Application

`podman pod ps` gives the summary view:

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED         INFRA ID      # OF CONTAINERS
7f6e5d4c3b2a  webapp      Running     3 minutes ago   c1d2e3f4a5b6  3
----

Inspect the pod, filtered to the state of the application:

[source,bash,role=execute]
----
podman pod inspect webapp --format '{{.State}} {{.NumContainers}}'
----

[source,text]
----
Running 3
----

Running, with three containers: the two pieces and the infra container. One line — the state of the whole application.

From the host, the page is served:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: 1, served from store at localhost:6379</p>
</body>
</html>
----

Load it again:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: 2, served from store at localhost:6379</p>
</body>
</html>
----

The count proves the pieces talk. Compare the two setups: on a network, the frontend needed a network join and an environment variable; in the pod, it needed a flag. The pod solved the networking by removing it — one lifecycle, one network view, one hostname the pieces agree on.

== Only the Right Port Opens

The store lives in the same pod as a reachable service. Try it from the host anyway:

[source,bash,role=execute]
----
curl http://localhost:6379
----

[source,text]
----
curl: (7) Failed to connect to localhost port 6379 after 0 ms: Couldn't connect to server
----

Only port 8000 was published — once, at the pod level, for the whole application. The pod exposes exactly what you told it to. The same isolation you relaxed for the frontend is still keeping the store private.

The application is one pod. The next module: managing it.
