= Letting the Right Traffic In

Your application is one pod, and the pieces talk: the startup log showed the frontend reach the store over the shared localhost. But from outside, nothing gets in — the pod has published no ports. In this module you will open the pod to its users, and see how little needs to open.

Access is deliberate. These images expose nothing by default. Everything that gets in gets in because you opened it.

== The Pod Publishes Nothing

From the host, try the page:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
curl: (7) Failed to connect to localhost port 8000 after 0 ms: Couldn't connect to server
----

The `web` container is listening on 8000 — but the connection is refused. The frontend is inside the pod, and the pod has not published any ports to the host. This is the isolation doing its job: a pod shares one network view internally and exposes nothing externally unless you tell it to.

== Publish a Port at the Pod Level

Recreate the pod with a published port. First stop and remove the current pod — this removes every container in it, which is the point of a pod:

[source,bash,role=execute]
----
podman pod stop webapp && podman pod rm webapp
----

Create the pod again, this time publishing port 8000 on the host to port 8000 in the pod:

[source,bash,role=execute]
----
podman pod create --name webapp -p 8000:8000
----

Note where the flag went: on the pod, not on any container. Port publishing is a property of the pod's network namespace — the infra container holds it, and every container in the pod shares it.

== Run the Application

[source,bash,role=execute]
----
podman run --pod webapp -d --rm --name web webcounter-app:latest
----

[source,bash,role=execute]
----
podman run --pod webapp -d --rm --name store registry.access.redhat.com/hi/valkey:latest
----

From the host, the page is now served:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: 1, served from store at localhost:6379</p>
</body>
</html>
----

Load it again:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<!DOCTYPE html>
<html>
<head><title>WebCounter</title></head>
<body>
<h1>WebCounter</h1>
<p>Page views: 2, served from store at localhost:6379</p>
</body>
</html>
----

Every page load is the frontend querying the store and incrementing the count: two containers in one pod, talking over the shared localhost, with the number to prove it. The store has no published port and no address you ever needed — the pieces talk privately, and the page is the evidence.

== Only the Right Port Opens

The store lives in the same pod as a reachable service. Try it from the host anyway:

[source,bash,role=execute]
----
curl http://localhost:6379
----

[source,text]
----
curl: (7) Failed to connect to localhost port 6379 after 0 ms: Couldn't connect to server
----

Only port 8000 was published. The store stays inside: the pod exposes exactly what you told it to — one port, the one the users need — no matter how many containers it holds. The same isolation you relaxed for the frontend, deliberately, at the pod level, is still keeping the store private.

Your users can now reach the web frontend, and the two pieces talk privately behind it. A pod is one way to let two containers talk. In the next module, you will take the pod apart and let them talk by name instead.
