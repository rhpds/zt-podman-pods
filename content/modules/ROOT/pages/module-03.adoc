= Managing the Pod

The application is one pod: two pieces talking over shared localhost, the page reachable on one published port, one lifecycle. In this module you will manage it — stop it and start it as one thing, read everything it writes, see what is running inside it, and operate on the pieces without taking the application apart.

== Stop the Application, Start It Again

The application has one lifecycle. Stopping it is one command, and it stops every piece in it:

[source,bash,role=execute]
----
podman pod stop webapp
----

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED         INFRA ID      # OF CONTAINERS
7f6e5d4c3b2a  webapp      Exited      5 minutes ago   c1d2e3f4a5b6  3
----

One command stopped the frontend, the store, and the infra container that holds them together. This is what the pod bought you: in module-01, two pieces meant two stop sequences in the right order; the application stops as one thing.

Starting it is one command too:

[source,bash,role=execute]
----
podman pod start webapp
----

The published port comes back with the pod. Reload http://webcounter-{guid}.{domain}/[*the web counter*^] in your browser: the page renders again, and the count kept going — `3`, one more than module-02 left it.

image::webcounter-pod-start.png[]

The store is the same container it was before the stop — stopped is not removed — and its data came back with it. What actually resets the count is replacing the store, which is the next lesson.

== Logs: One Command, Every Container

There is no logging into these containers — they have no shell. What the applications write is the debugging surface, and the pod returns all of it at once:

[source,bash,role=execute]
----
podman pod logs webapp
----

[source,text]
----
00335c55bc34 [2026-10-20 14:05:58 +0000] [1] [INFO] Starting gunicorn 23.0.0
00335c55bc34 store reached at localhost:6379
066f5d153c67 1:M 20 Oct 2026 14:05:58.904 * Valkey version=9.0.6, bits=64, commit=00000000, modified=0, pid=1, just started
066f5d153c67 1:M 20 Oct 2026 14:05:58.909 * Ready to accept connections tcp
----

One command, every container's logs — each line prefixed with the ID of the container it came from: the frontend's gunicorn startup and the store's valkey startup, interleaved as they happened. When something in the application misbehaves, you look at the pod, not at its pieces one at a time.

== What Is Running Inside

Logs show what the applications said. For what they are doing, the pod answers in one command:

[source,bash,role=execute]
----
podman pod top webapp
----

[source,text]
----
USER        PID         PPID        %CPU        ELAPSED       TTY         TIME        COMMAND
0           1           0           0.000       5.2s          ?           0s          /catatonit -P
65532       1           0           0.000       5.2s          ?           0s          /app/venv/bin/python3 /app/venv/bin/gunicorn --workers 2 --bind 0.0.0.0:8000 app:app
65532       2           1           0.000       4.2s          ?           0s          /app/venv/bin/python3 /app/venv/bin/gunicorn --workers 2 --bind 0.0.0.0:8000 app:app
65532       3           1           0.000       4.2s          ?           0s          /app/venv/bin/python3 /app/venv/bin/gunicorn --workers 2 --bind 0.0.0.0:8000 app:app
65532       1           0           0.000       4.2s          ?           0s          /usr/bin/valkey-server *:6379
----

The processes of every container in the pod, in one table — no shell required. The first row is the infra container's tiny process holding the pod open; the frontend is gunicorn with its two workers; the store is valkey's server process. Note the two PID 1s: each container has its own PID namespace — the pod shares the network namespace, not every namespace. When a piece misbehaves, this is how you see inside it without a shell.

== Restart a Piece

The pod operates as one thing — and individual pieces can still be operated on inside it. A piece misbehaves; restart it without touching the rest of the application:

[source,bash,role=execute]
----
podman restart web
----

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED         INFRA ID      # OF CONTAINERS
7f6e5d4c3b2a  webapp      Running     6 minutes ago   c1d2e3f4a5b6  3
----

The pod never stopped — the frontend restarted inside it, and the other pieces were never touched. The restart is one command: no container removal, no re-running the original command, the piece comes back inside the same pod.

For how much the application is using, the pod answers in one command:

[source,bash,role=execute]
----
podman pod stats webapp --no-stream
----

[source,text]
----
POD           CID           NAME                CPU %       MEM USAGE/ LIMIT   MEM %       NET IO       BLOCK IO    PIDS
4408f687415b  3873ce2b0dc5  4408f687415b-infra  0.19%       278.5kB / 33.27GB  0.00%       258B / 542B  -- / --     1
4408f687415b  00335c55bc34  web                 9.54%       40.51MB / 33.27GB  0.12%       258B / 542B  -- / --     3
4408f687415b  066f5d153c67  store               1.13%       4.231MB / 33.27GB  0.01%       258B / 542B  -- / --     6
----

The resource usage of the whole application — CPU, memory, network I/O, one row per container — in one command. One pod, one view.

== Replace a Piece

Restarting keeps the same container. Replacing it is different: a stopped container is not a removed container — stopping the store leaves it behind, Exited, still holding its name. Removing it frees the name, and a fresh container takes its place:

[source,bash,role=execute]
----
podman stop store
----

[source,bash,role=execute]
----
podman rm store
----

[source,bash,role=execute]
----
podman run --pod webapp -d --name store registry.access.redhat.com/hi/valkey:latest
----

Check that the application is unaffected:

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED         INFRA ID      # OF CONTAINERS
7f6e5d4c3b2a  webapp      Running     8 minutes ago   c1d2e3f4a5b6  3
----

The pod never stopped: the new store container joined the pod's shared localhost, and the frontend found it the way it found the old one.

Reload the page in your browser: the count went back to `1`.

image::webcounter-replace.png[]

The store's state lived in the container that was replaced. The pod kept running; only the piece changed.

== Take the Application Down

The whole application comes down the way it went up — one pod, one command:

[source,bash,role=execute]
----
podman pod stop webapp && podman pod rm webapp
----

One command stopped and removed the infra container and every piece in it. The application is one thing, and it comes down as one thing — which is what "one application" means.
