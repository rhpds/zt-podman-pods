= How Podman Networks Operate

Your application ran as a pod: the pieces talked over the shared localhost, and the page was reachable on one published port. A pod is one way to let two containers talk. A network is the other. In this module you will run the same application without a pod, join the containers to a user-defined network, and watch the frontend find the store by name.

== Take the Pod Apart

One command stops the infra container and every service in it:

[source,bash,role=execute]
----
podman pod stop webapp && podman pod rm webapp
----

The pieces lived and died together — that is what "one application" meant.

== The Usual Fashion, Again

Run the two pieces in the usual fashion — independent containers, no pod:

[source,bash,role=execute]
----
podman run -d --rm --name web -p 8000:8000 webcounter-app:latest
----

[source,bash,role=execute]
----
podman run -d --rm --name store registry.access.redhat.com/hi/valkey:latest
----

From the host, the page:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<p>Page views: —</p>
<p>The web frontend cannot reach its data store at localhost:6379.</p>
----

The same failure as the first module: without a pod, the frontend's `localhost` is its own container, and the store is not there. The frontend needs the store's address — and chasing addresses is the problem: they change every time a container is recreated. What it needs is a name that resolves, on a network both containers join.

== Create a Network

[source,bash,role=execute]
----
podman network create app-net
----

So far every container has used Podman's default network, which every container joins automatically. A user-defined network is different: containers join it by choice. Membership is what makes containers visible to each other.

== Join the Pieces by Name

Recreate both containers on the network. Because they were started with `--rm`, stopping them removes them:

[source,bash,role=execute]
----
podman stop web store
----

Run the store on the network first:

[source,bash,role=execute]
----
podman run -d --rm --name store --network app-net registry.access.redhat.com/hi/valkey:latest
----

Now the frontend, on the same network, pointing at the store by its container name. One environment variable is all that changes:

[source,bash,role=execute]
----
podman run -d --rm --name web -p 8000:8000 --network app-net -e STORE_HOST=store webcounter-app:latest
----

From the host, the page is served — and it says where the store was found:

[source,bash,role=execute]
----
curl http://localhost:8000
----

[source,text]
----
<p>Page views: 1, served from store at store:6379</p>
----

The frontend reached the store at `store:6379`. `store` is not an address — it is the container's name, resolved through the network's DNS. No pod, no shared localhost: the network is what let two containers find each other, and the name is how. The only difference from the failing run is one environment variable.

== Who Is on the Network

The network is an object you can inspect. Filter its output to the members:

[source,bash,role=execute]
----
podman network inspect app-net --format '{{range .containers}}{{.name}} {{end}}'
----

[source,text]
----
store web
----

Both containers, listed by name — the same names the frontend resolved. The network's members are its communication boundary: containers on it can find each other by name, and containers off it cannot.

== Clean Up

The application is two containers on a network. Stopping them removes them — they were started with `--rm`:

[source,bash,role=execute]
----
podman stop web store
----

The network stays behind until you remove it:

[source,bash,role=execute]
----
podman network rm app-net
----

Two ways to let containers talk, one application: a pod gives its containers one localhost and one lifecycle; a network gives containers names and a boundary you join by choice. The same application ran both ways — the only difference was one environment variable.
