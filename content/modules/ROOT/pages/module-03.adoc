= Managing the Pod

Now that we have the application in a pod, how do we manage it?
When it was two separate containers, we had to do that individually and coordinated by hand.
This module will look at how containers run (and stop) inside a pod and how we can still individually control them if needed.

== Stop the Application, Start It Again

An application has one lifecycle. 
Stopping it should be one command, and it shoudl stop every component.

[source,bash,role=execute]
----
podman pod stop webapp
----

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED         INFRA ID      # OF CONTAINERS
7f6e5d4c3b2a  webapp      Exited      5 minutes ago   c1d2e3f4a5b6  3
----

Once it's been defined, the whole pod now operates as a single unit.
We can now think about this as the `webapp` instead of the application made up of the `web` and `store` containers.

Starting it is one command too:

[source,bash,role=execute]
----
podman pod start webapp
----

The published port comes back with the pod. 
Reload http://webcounter-{guid}.{domain}/[*the web counter*^] in your browser.
The page renders again, and the count kept going from where you left it.

image::webcounter-pod-start.png[]

The store is the same container it was before the stop and its data is still in the container.
What actually resets the count is replacing the store, which is the next lesson.

== What Is Running Inside

Logs show what the applications said. For what they are doing, the pod answers in one command:

[source,bash,role=execute]
----
podman pod top webapp
----

[source,text]
----
USER        PID         PPID        %CPU        ELAPSED       TTY         TIME        COMMAND
0           1           0           0.000       5.2s          ?           0s          /catatonit -P
65532       1           0           0.000       5.2s          ?           0s          /app/venv/bin/python3 /app/venv/bin/gunicorn --workers 2 --bind 0.0.0.0:8000 app:app
65532       2           1           0.000       4.2s          ?           0s          /app/venv/bin/python3 /app/venv/bin/gunicorn --workers 2 --bind 0.0.0.0:8000 app:app
65532       3           1           0.000       4.2s          ?           0s          /app/venv/bin/python3 /app/venv/bin/gunicorn --workers 2 --bind 0.0.0.0:8000 app:app
65532       1           0           0.000       4.2s          ?           0s          /usr/bin/valkey-server *:6379

You get a full table of all of the processes in each of the containers of the pod in one place.
Notice that there are 3 PID 1s.
Each container still gets it's own PID namespace, the pod doesn't create all of the namespaces as shared.

== Replace a Piece

Restarting keeps the same container, but what if we had an updated container and needed to replace a component?

A stopped container isn't removed. 
It's down but not gone.
We need to remove it in order to replace it.

[source,bash,role=execute]
----
podman stop store
----

[source,bash,role=execute]
----
podman rm store
----

Check the state of our pod without the `store`

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED         INFRA ID      # OF CONTAINERS
7f6e5d4c3b2a  webapp      Running     8 minutes ago   c1d2e3f4a5b6  2
----

Now launch a new `store` container.
For purposes of the lab, we're using the same image but the outcome would be the same if `latest` here was newer.
[source,bash,role=execute]
----
podman run --pod webapp -d --name store registry.access.redhat.com/hi/valkey:latest
----

Check that the application is unaffected:

[source,bash,role=execute]
----
podman pod ps
----

[source,text]
----
POD ID        NAME        STATUS      CREATED         INFRA ID      # OF CONTAINERS
7f6e5d4c3b2a  webapp      Running     8 minutes ago   c1d2e3f4a5b6  3
----

The pod never stopped: the new `store` container joined the pod and the webapp found it the way it found the old one.

Reload the page in your browser: the count went back to `1`.

image::webcounter-replace.png[]

The state lived in the container that was replaced. 
The pod kept running, but the data in the original container was lost.

== Take the Application Down

The whole application comes down the way it went up — one pod, one command:

[source,bash,role=execute]
----
podman pod stop webapp && podman pod rm webapp
----

Grouping containers in logical units gives us a useful way to treat them as a single application.
We've only done the basics of pod management in this lab, but this can make managing containerized applications comprised of multiple components much easier.
Communitcation via shared namespace is one benefit, but resource controls can also be set once instead of for each container.

With containers grouped together, creating system services from them becomes a lot easier as well.
Check out our other labs to see how `quadlets` can quickly take your pods into services and how they lend themselves to automation.
